## 一、问题是什么

已发布的 v0.0.14 Release Notes 里，R-01 披露表格有一行：

> | **风险接受按版本单独作出** | 此前某版本的一次性风险接受**不构成 v0.0.14 的授权**；
> 本版本公开发布须在完整披露 R-01 的前提下单独确认 | **待主人裁决** |

而 v0.0.14 **已经公开发布了**。一个"已发布版本"的说明里写着"待主人裁决"，
描述的是一个**不可能存在的状态** —— 它能发出来，本身就说明授权已作出。

### 成因（不是笔误，是模板缺陷）

`release.yml` 的 Release Notes 模板把这一行**写死**成待定态。
模板在 v0.0.13 时期编写，当时确实没授权；发布时没有任何机制去更新它。

### 已修的部分（本轮，不影响已发布内容）

| 项 | 状态 |
|---|---|
| 模板改为「本版本已单独确认」+ 新增一行指向 `docs/RISK_DECISION___VERSION__.md` | ✅ 已修（提交待提交） |
| 静态护栏禁止模板再出现「待主人裁决 / 待授权 / 待批准」 | ✅ 已加（含负向对照） |
| 发布预演会检查模板是否含待定态措辞 | ✅ 已加（`preflight-dryrun.mjs --mode=static`） |
| v0.0.14 线上 Release Notes | ❌ **仍含该行** —— 需要授权才能改 |

## 二、这笔瑕疵有多严重？（如实评估）

**不影响风险披露的完整性。** R-01 的七项实质披露全部在场且准确：

| # | 披露项 | 线上实际内容 |
|---|---|---|
| 1 | 原站素材曾进入历史提交 | ✅ 有 |
| 2 | 当前主分支不再包含 | ✅ 有（含逐模式零命中的说明） |
| 3 | 旧 Tag / 历史引用仍可能可访问 | ✅ 有（标注「仍然存在」） |
| 4 | 历史风险尚未根治 | ✅ 有（标注 DEFERRED） |
| 5 | 本轮未执行历史改写或 force push | ✅ 有 |
| 6 | 新代码 / 安装包 / 镜像经过独立扫描 | ✅ 有 |
| 7 | 后续仍需单独处置 | ✅ 有 |

**唯一失真的是一行状态列的措辞。** 它不会让读者误以为「有版权授权」，
也不会让读者误以为「历史已清理」—— 它只会让读者困惑「这版到底授权没授权」。

> 需要说明的反向风险：若读者按字面理解成「v0.0.14 未授权就发布了」，
> 那会让人怀疑发布流程的合规性。**这是本瑕疵真正的危害**，
> 而不是"少写了一个状态"。

## 三、三个可选方案

### 方案 A（推荐）：**只改这一行，其余一字不动**

| 项 | 内容 |
|---|---|
| 操作 | `PATCH /repos/{owner}/{repo}/releases/439444090`，body 里做**单行替换** |
| 改动量 | 1 行（`待主人裁决` → `本版本已单独确认`） |
| 是否改变资产 | 否（不动 ZIP / SHA256SUMS） |
| 是否改变 Tag | 否 |
| 是否改变发布时间 / id | 否（GitHub 保留 `created_at`，只会更新 `updated_at`） |
| 可逆性 | 改回去也只能再 patch 一次，**原始版本不留存**（无编辑历史） |
| 风险 | 极低。但仍是「修改已发布内容」这一行为 |

**具体替换**（只替换状态列这一个词，句子其余部分保持原样）：

```
- | **风险接受按版本单独作出** | 此前某版本的一次性风险接受**不构成 v0.0.14 的授权**；本版本公开发布须在完整披露 R-01 的前提下单独确认 | 待主人裁决 |
+ | **风险接受按版本单独作出** | 此前某版本的一次性风险接受**不构成 v0.0.14 的授权**；本版本公开发布须在完整披露 R-01 的前提下单独确认 | **本版本已单独确认**（裁决记录：`docs/RISK_DECISION_v0.0.14.md`） |
```

### 方案 B：**加一条勘误说明，不改原文**

| 项 | 内容 |
|---|---|
| 操作 | 在 Notes **末尾**追加一小节：「勘误（2026-11-10）：上表'待主人裁决'一行系模板遗留，本版本发布时已获明确授权，见 `docs/RISK_DECISION_v0.0.14.md`」 |
| 改动量 | 追加 2~3 行 |
| 优点 | **原文保留**，读者能同时看到"当时写了什么"和"后来更正了什么" |
| 缺点 | 正文里仍留着那句错话；追加内容在长文末尾，容易被忽略 |
| 可逆性 | 同上，无历史留存 |

### 方案 C：**不改，只在仓库文档披露**

| 项 | 内容 |
|---|---|
| 操作 | 什么都不做 |
| 优点 | **零不可逆操作**；符合「不修改已发布 Release」的既有纪律 |
| 缺点 | 线上说明持续含一句与事实相反的陈述 |
| 现状 | 本轮**已按此执行** —— 详见 `RELEASE_GATE.md` §8.5 |

## 四、建议

**建议采用方案 A**，理由：

1. 改动是**单行状态词**，不涉及任何实质披露内容的增删；
2. 它修正的是「一句与事实相反的话」，而不是"美化措辞"；
3. 不改资产、不改 Tag、不改发布时间，对外部引用的破坏为零；
4. 若保留原样，任何按字面读的读者都会得到「本版未授权发布」的错误结论 ——
   这对项目可信度的损害，大于"修改过一次 Release"这件事本身。

**但不建议在本轮（未获授权时）执行。** 若主人选择方案 C，
本轮已完成的披露（`RELEASE_GATE.md` §8.5）足以让仓库内的记录保持真实。

## 六、这件事的根本教训（已固化）

**Release Notes 里的"状态性陈述"不能写死在模板里。**
模板在编写时刻是正确的，但发布时刻的事实可能已经变了。

已做的事：

1. 模板改为**事实中性**的表述（不声明"待裁决"，也不声明"已授权"，而是
   「本版本已单独确认」+ 指向决策记录文件 —— 后者是**可核验**的）；
2. 加静态护栏：模板不得出现「待主人裁决 / 待授权 / 待批准」；
3. 加发布预演检查：`preflight-dryrun.mjs --mode=static` 会扫模板正文；
4. 加发布预演检查：渲染出的 Notes 会检查 R-01 披露是否在场。

⇒ **后续版本不会再复现这一类"发布后自证未授权"。**
