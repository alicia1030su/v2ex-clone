# 搜索方案实测与选型报告（v0.0.5）

> 任务书 §六：「不能简单使用英文 FTS 配置就宣称中文全文搜索已经完成」，
> 「如果 PostgreSQL 原生方案不能满足中文搜索质量，**先进行实际对比测试**，
> 再选择适合的扩展或替代架构」。
>
> 本报告是**实测记录**，不是设计构想。所有数字都来自
> `scripts/perf/search-benchmark.ts` 在真实 PostgreSQL 上的运行。

---

## 一、问题：v0.0.4 的搜索对中文不够用

v0.0.4 的实现是单条 `ILIKE '%关键词%'`（配合 `pg_trgm` GIN 索引加速）。
这对英文没问题，但**中文没有空格分词**：

| 查询 | 文档标题 | v0.0.4 结果 |
|---|---|---|
| `数据库性能优化` | 数据库性能优化的实践 | ✅ 命中（连续） |
| `数据库性能优化` | 优化实践与数据库性能的关系 | ❌ **漏掉**（词序被打散） |
| `性能` | 数据库性能优化的实践 | ✅ 命中 |

中文用户搜「数据库性能优化」时，期望的是「这些词都出现」，
而不是「这几个字必须连在一起」。

## 二、四个方案的横向实测

### 2.1 实测数据

- **语料**：`tests/v005-search-quality.spec.ts` 里的 10 条代表性文档
  （中文 / 英文 / 中英混合 / 特殊符号）
- **对比对象**：
  1. `ILIKE` 整串（v0.0.4 现状）
  2. `pg_trgm` 相似度（`similarity(title, kw) >= 0.3`）
  3. PostgreSQL FTS（`to_tsvector('simple', ...)`）
  4. **CJK bigram**（本轮自研，见 §三）

### 2.2 关键实测结论

| 方案 | 中文效果 | 依赖 | 结论 |
|---|---|---|---|
| `ILIKE` 整串 | 差（必须连续） | 无 | 现状，不够用 |
| `pg_trgm` 相似度 | 中（模糊但噪声大） | 需 pg_trgm | 适合做**排序辅助**，不能当主条件 |
| FTS `simple` | **几乎无用** | 无 | ❌ 不切中文，整句当一个词 |
| FTS `zhparser` / `pg_jieba` | 好 | **需装扩展** | ❌ **本机 PG 没有编译这两个扩展** |
| **CJK bigram** | **好** | **无** | ✅ **采用** |

### 2.3 为什么不能依赖中文分词扩展

实测 `pg_available_extensions`（本机 PostgreSQL 17.5）：

```
AVAILABLE: [{"name":"pg_trgm","default_version":"1.6"}]
```

**`zhparser` 与 `pg_jieba` 都不在列表里** —— 它们没有编译进官方镜像的 PG。
依赖它们意味着「换个 PG 版本 / 换个基础镜像就装不上」，
与任务书「维护成本低、与 Docker 部署兼容」的要求直接冲突。

**结论：中文分词必须自研，且只能依赖 PostgreSQL 原生能力。**

## 三、采用的方案：CJK bigram

### 3.1 算法

- **CJK 字符**（中日文）：取**相邻二元组**（bigram）
  - 「性能优化」→ 「性能」「能优」「优化」
- **拉丁字母 / 数字**：按**非字母数字**边界切成完整词
  - `optimize` 不会被拆成 `op`/`pt`/`ti`
- **其余字符**：忽略

### 3.2 bigram 为什么够用

1. 覆盖所有连续二元组合 ⇒ 任意子串都能被匹配到
2. **不依赖词典** ⇒ 零维护成本、无新词失效问题
3. 与既有 `pg_trgm` 索引天然契合（bigram 串可用 trigram 索引加速）

### 3.3 生产实现

`src/lib/search-tokenize.ts`：

| 函数 | 用途 |
|---|---|
| `tokenizeSearchQuery()` | 切词（bigram + 拉丁整词） |
| `buildSearchPatterns()` | **OR 语义**模式（整串 + bigram） |
| `buildAndSearchPatterns()` | **AND 语义**模式（全部 bigram 都要命中） |
| `toLikePattern()` | 转义 LIKE 元字符（`%` `_` `\`） |
| `limitSearchTokens()` | token 数上限（64）防超长查询拖垮索引 |

## 四、关键设计决策：为什么是**两阶段搜索**

### 4.1 三种策略的实测对照

`scripts/perf/search-benchmark.ts`，**5000 主题**规模（长尾分布：
每 50 条才有一条含目标关键词），`title` / `content` 各带 GIN trigram 索引：

| 策略 | 召回行数 | P50 | P95 | P99 |
|---|---|---|---|---|
| ① ILIKE 整串（v0.0.4 现状） | 60 | **1ms** | 15ms | 19ms |
| ② bigram **OR**（任一 token 命中） | **5000** ❌ | 1ms | 1ms | 1ms |
| ③ bigram **AND**（全部 token 命中） | **60** ✅ | 15ms | 17ms | 18ms |

### 4.2 解读

- **② OR 的假阳性不可接受**：搜「数据库性能优化」会产生
  「数据库」「据库」「库性」「性能」「能优」「优化」等 token，
  任一命中即算 ⇒ 只要文档含「优化」就被召回（5000/5000 全中）。
- **③ AND 的精度与整串持平**（60 行 vs 60 行），只是慢一点（P50 15ms vs 1ms）。

### 4.3 最终策略

```
阶段 1：ILIKE 整串匹配（快，命中 trigram 索引）
   ↓ 若 total === 0
阶段 2：bigram AND 回退（慢一点，但能召回「词序被打散」的中文文档）
```

这样既**不劣化** v0.0.4 的性能（P50 仍是 1ms），
又**提升**了中文召回（阶段 1 漏掉的、阶段 2 能找到）。

**回退只在「含 CJK 的关键词」时启用** —— 纯 ASCII 关键词的
`andPatterns` 就是整串本身，重复查一次没意义。

## 五、性能对照报告（生产配置实测）

### 5.1 环境

- PostgreSQL 17.5（Windows，本地隔离实例 `127.0.0.1:55440`）
- 5000 个主题（长尾分布），`title` / `content` 各一个 `GIN (… gin_trgm_ops)` 索引
- 60 次查询（40 次中文 + 20 次英文混合）
- 索引与生产一致（`drizzle/0002_v004_perf_indexes.sql`）

### 5.2 结果

| 查询类型 | 次数 | P50 | P95 | P99 | 平均返回行数 |
|---|---|---|---|---|---|
| **① ILIKE 整串**（中文） | 40 | 1ms | 15ms | 19ms | 60 |
| **① ILIKE 整串**（英文） | 20 | 1ms | 16ms | 20ms | 0 |
| **② bigram OR**（中文） | 40 | 1ms | 1ms | 1ms | **5000**（假阳性） |
| **② bigram OR**（英文） | 20 | 1ms | 1ms | 1ms | **5000**（假阳性） |
| **③ bigram AND**（中文） | 40 | 15ms | 17ms | 18ms | 60 |
| **③ bigram AND**（英文） | 20 | 1ms | 1ms | 2ms | 0 |

### 5.3 索引使用的实测说明

第一版数据（**所有**标题都含「数据库性能优化」）测出 **Seq Scan** ——
这不是 trigram 索引的问题，而是**数据分布**的问题：
关键词命中 60% 的行 ⇒ 索引选择性太差 ⇒ 优化器主动放弃索引。

改成长尾分布（每 50 条命中 1 条）后，
整串匹配的 P50 从 **17ms → 1ms**（命中索引）。

> **这说明索引效果依赖数据分布，而不是「建了索引就一定快」。**
> 真实论坛的关键词分布天然是长尾的，所以生产表现对应长尾那一行。

## 六、安全与副作用

| 项 | 结论 |
|---|---|
| SQL 注入 | ✅ 所有模式**参数化**传入（drizzle `sql` 模板）；`%` `_` `\` 已转义 ⇒ 无法变成通配符 |
| 全表扫描 | ✅ LIKE 元字符转义后用户输入无法构造通配符；纯符号输入直接判定为「无法分词」⇒ 不查库 |
| 发帖 / 回复性能 | ✅ **不受影响** —— 分词只在**搜索路径**发生，发帖 / 回复不调用它 |
| 分页正确性 | ✅ E2E 验证 `total` / `totalPages` / `limit` 钳制 |
| token 数上限 | ✅ 64 —— 超长查询不会产生过多 SQL 条件 |

## 八、已知限制（如实标注）

1. **bigram 是子串级匹配，不是词级匹配** ——
   搜「性能优化」会召回含「能优」的文档（假阳性）。
   本轮用「阶段 1 整串 + 阶段 2 AND 回退」把影响控制住，
   但**没有**实现真正的词级分词（那需要词典或扩展）。

2. **没有排序权重** ——
   当前排序是「标题命中 → 回复数 → 时间」。
   bigram 命中的数量**不参与排序** ⇒ 多命中 bigram 的文档不会排在前面。

3. **没有拼音 / 简繁转换** ——
   搜「性能」找不到「性能」的拼音输入（`xingneng`）。
   V2EX 原站同样不支持，故不实现。

4. **FTS 仍是英文场景的更好选择** ——
   如果将来要做英文全文检索（词干还原、位置排序），
   应在 bigram 之外**增加** FTS 通道，而不是替换。

5. **本轮实测规模是 5000 主题** ——
   v0.0.4 的压测规模是 10 万主题 / 100 万回复。
   搜索路径的规模效应**未在 10 万量级复测**。
   （10 万量级的搜索压测留给 v0.0.5 的性能阶段 P2。）

## 九、复现方式

```bash
# 性能对照（自动建库，结束后清理临时表）
npx tsx scripts/perf/search-benchmark.ts \
  --db=postgres://v2ex:xxx@127.0.0.1:55440/v2ex_searchbench \
  --topics=5000 --queries=40 --verbose

# 单元测试
npx vitest run tests/v005-search-quality.spec.ts tests/v005-search-tokenize.spec.ts

# 端到端（需要先启动应用与测试 PG）
npx playwright test e2e/v005-search.spec.ts
```
