### P0-1 通知系统真实双用户验收 —— ✅ 完成（并修掉一个真实泄露）

**做了什么**

- `e2e/v015-notifications.spec.ts`（8 条）：每个用户独立 `BrowserContext`（独立 Cookie），
  全部走真实 HTTP 路由（真实 CSRF / 限流 / DB）。
- `tests/v015-notifications-db.spec.ts`（17 条真库）：把判据按组合矩阵钉死。
- `src/server/notifications.ts`（新增）：可见性判据收敛到一处。

**发现的真实缺陷**

通知的 `message` 是**写入时**拼好的字符串，里面嵌了主题标题。
而 `GET /api/notifications` 与 `/notifications` 页面**完全不 join topics / nodes** ⇒
节点 hidden / 主题软删之后，公共页面已 404，**通知收件箱仍返回那条标题**。
「提及通知」的收件人是**任意第三方** ⇒ 真实跨用户泄露。

**修复过程中我自己引入过一个回归（已修）**

`action=accept` 处理举报时会先**软删被举报主题**，再写 `type='system'` 的通知 ——
那条通知的 topicId 指向刚被删的主题，于是被"只判断主题可见性"的判据一起过滤
⇒ **举报人永远收不到处理结果**。已在判据中显式放行 `system` 类型，并补 3 条真库用例。

**覆盖矩阵与「不适用」项**

| 事件 | 产品是否设计 | 覆盖 |
|---|---|---|
| 回复通知 | ✅ | E2E + 真库 |
| @ 提及 | ✅ | E2E + 真库 |
| 感谢回复（`topic_thanks`） | ✅ | E2E（含重复感谢幂等） |
| 系统通知（举报处理结果） | ✅ | E2E + 真库（含「带 topicId 且主题已删」） |
| 收藏 | ❌ **不适用**（`/api/collections` 从不写通知） | 断言「确实不产生」 |
| 节点感谢（`node_thanks`） | ❌ **不适用**（枚举有，全仓零写入点） | 断言「从未出现」，**不凭空新增** |

另覆盖：未读数 / 单条已读 / 全部已读 / 刷新后保留 / 多用户真并发（`Promise.all`）/

## 7. 环境坑（本轮新增）

- **`git filter-branch` 的 `--tag-name-filter cat` 不可省**：漏掉它时 annotated tag
  不会跟着改写，`git cat-file` 仍能从旧 SHA 取到素材 —— 会得出「清理无效」的假结论。
  第一版演练就踩了这个（清理后 5 个素材路径仍 `STILL REACHABLE`）。
- **必须删 `refs/original` + `reflog expire --expire=now --all` + `gc --prune=now`**，
  否则旧对象仍在库中，`cat-file` 照样能读到。
- **审计口径混用会得出自相矛盾的数字**：第一版把 `local-*.png` 算进「受影响对象」，
  得到 68，与历史报告的 81 对不上；两个数字都"像算过"，极难发现。
  ⇒ 任何「N 个对象」的结论都必须同时打印**构成明细**。
- **可达性判定若用错口径会把风险虚报成 100%**：第一版用「证据文件」口径判定 refs，
  结果 39/39 分支、9/9 Tag 全部"current-tree"（因为 `local-*.png` 在 master 上本来就跟踪）。
- **本机 `CODEBUDDY_SAFE_DELETE_ENABLED=1` 会拦截 `rm -rf`**：
  `filter-branch` 清理 `.git-rewrite` 时被拦，报 `SAFE_DELETE_FAIL_CLOSED`。
  脚本里应写成 `rm -rf ... 2>/dev/null || true`，且**不让清理失败污染退出码**。
- **`/tmp` 与 Windows 路径不通用**：`curl -o /tmp/x` 写的是 MSYS 的 `/tmp`，
  而 `python` 读 `/tmp/x` 会 `FileNotFoundError`。跨工具传文件要落在**仓库内**的临时目录。

## 8. 已知取舍

- **通知可见性采用「读取时过滤」而不是「写入时清洗」**：
  消息文本保留了当时的标题（作为历史记录），只在读取时按当前可见性过滤。
  好处是节点恢复 active 后通知自动重新可见（真库用例已覆盖）；
  代价是数据库里确实存了那些标题 —— 这是有意的（否则节点临时隐藏就永久损坏历史记录）。
- **`system` 通知不受主题可见性过滤**：它不含主题内容（文案是"你举报的内容已被处理"），
  且若过滤会导致举报人永远收不到处理结果。已在真库用例中钉死。
- **发布预演不覆盖「真实推 Tag 后的行为」**：它验证的是链路判据与失败传播，
  不是「Tag 推上去后 GitHub 实际怎么调度」。后者无法在不推 Tag 的前提下验证 —— 属已知边界。
- **R-01 的 PR ref 残留无法消除**：`refs/pull/N/head` 是 GitHub 的只读衍生引用，
  仓库方无法删除。这是「只改写分支 + Tag」清理不完整的根本原因。
