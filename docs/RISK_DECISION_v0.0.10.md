## 三、本轮新发现的两个事实（与 v0.0.9 相比）

### 3.1 v0.0.9 的公开资产确实带缺陷（这加强了发布 v0.0.10 的必要性）

| 缺陷 | 事实 |
|---|---|
| V9-09 脚本缺可执行位 | `v0.0.9` Tag（`80a3b8c`）**落后 master 8 个提交**，修复提交 `d4892b9` 不在 Tag 内 ⇒ 已发布的 ZIP 里 `deploy/*.sh` 是 0644 |
| V9-13 SIGPIPE | 修复提交 `67b5e8b` 同样不在 Tag 内 ⇒ 已发布包的 `backup.sh` 会把**正常备份判成空**并删除 |

**这两个都不是理论风险**：用户在真实 Linux 上按文档执行 `./backup.sh`，
数据越多越必然失败（pg_dump 输出超过 64 KiB 管道缓冲即命中），
而且失败方向是「删掉好备份」。v0.0.10 是这两个修复的**唯一合法载体**
（已发布资产不可覆盖）。

### 3.2 本轮新增的门禁能拦住同类问题

`scripts/release/verify-release-consistency.sh` 把「源码 / Tag / 镜像 / ZIP /
README / Release」六项绑成一条门禁。实测：

- 期望 0.0.9 但源码是 0.0.10 ⇒ 8 项判红
- 版本全对但 ZIP 里脚本权限是 0644 ⇒ 点名 `deploy/backup.sh=0o100644` 并拒绝发布
- ZIP 文件名/包内版本/SHA256 任一不符 ⇒ 判红
